## 1. Что делает этот проект?

Это **серверное приложение** (backend) — программа, которая работает на сервере и отвечает на запросы от клиентов (например, от браузера или мобильного приложения).

Проект реализует **две ключевые вещи**:

1. **Аутентификацию** — проверку «Кто ты?». Пользователь вводит email и пароль, система проверяет их и выдаёт токен (электронный пропуск).

2. **Авторизацию** — проверку «Тебе можно?». Когда пользователь пытается что-то сделать, система проверяет, есть ли у него права на это действие.

А ещё есть **бизнес-объекты** (автомобили) — пример того, к чему применяется система прав. Это как в автосалоне: одни могут только смотреть машины, другие — редактировать, третьи — удалять.

## 5. Как данные хранятся в «базе»

Вместо настоящей базы данных (PostgreSQL) мы используем **JSON-файлы**.
JSON — это текстовый формат данных, похожий на словари Python.

### 5.1. Пользователи (users.json)

```json
{
  "id": "user-1",                    // Уникальный идентификатор
  "first_name": "Админ",             // Имя
  "last_name": "Админович",          // Фамилия
  "patronymic": "Админов",           // Отчество
  "email": "admin@test.ru",          // Email (используется для входа)
  "password_hash": "a1b2c3:d4e5f6",  // Хеш пароля (НЕ сам пароль!)
  "role_id": "role-admin",           // Ссылка на роль
  "is_active": true,                 // Активен ли аккаунт (false = удалён)
  "created_at": "2024-01-01T00:00:00" // Дата регистрации
}
```

**Важно:** `password_hash` — это НЕ пароль. Это результат математического преобразования пароля. Из хеша нельзя восстановить пароль.

### 5.2. Роли (roles.json)

```json
{
  "id": "role-admin",                // Уникальный идентификатор роли
  "name": "admin",                   // Название роли
  "description": "Администратор",    // Описание
  "permission_ids": [                // Список разрешений этой роли
    "perm-users-read",
    "perm-users-write",
    "perm-cars-read",
    ...
  ]
}
```

### 5.3. Разрешения (permissions.json)

```json
{
  "id": "perm-cars-read",           // Уникальный идентификатор
  "resource": "cars",               // К КАКОМУ ресурсу доступ
  "action": "read",                 // КАКОЕ действие разрешено
  "description": "Просмотр автомобилей"  // Человеческое описание
}
```

**Ключевая идея:** разрешение = ресурс + действие.
- `resource` — это ЧТО: пользователи, машины, роли, разрешения
- `action` — это ЧТО ДЕЛАТЬ: read (читать), write (писать), delete (удалять), manage (управлять)

### 5.4. Связи между таблицами

```
ПОЛЬЗОВАТЕЛЬ ──role_id──▶ РОЛЬ ──permission_ids──▶ РАЗРЕШЕНИЕ
                                      │
                                      ├── resource: "cars"
                                      └── action: "read"
```

Пользователь ссылается на роль через `role_id`.
Роль содержит список `permission_ids` — ссылки на разрешения.
Разрешение описывает конкретный ресурс и действие.

### 5.5. Чёрный список токенов (sessions.json)

```json
{
  "token": "eyJhbGciOi...",          // Сам JWT-токен
  "user_id": "user-1",               // Кто вышел
  "logout_at": "2024-01-01T12:00:00" // Когда вышел
}
```

Зачем нужен? JWT-токен — самодостаточный, сервер не хранит «сессии».
Чтобы разлогинить пользователя, мы записываем его токен в чёрный список.
При каждой проверке мы смотрим — нет ли этого токена в списке.

## 6. Как работает аутентификация (вход в систему)

**Аутентификация** = проверка «Кто ты?»

### Шаг за шагом:

```
1. Пользователь отправляет POST /users/login с email и паролем
   ↓
2. Система ищет пользователя с таким email в users.json
   ↓
3. Если не найден → ошибка 401 "Неверный email или пароль"
   ↓
4. Проверяет is_active. Если false → ошибка 401 "Аккаунт удалён"
   ↓
5. Хеширует введённый пароль с той же солью и сравнивает с password_hash
   ↓
6. Если не совпадает → ошибка 401 "Неверный email или пароль"
   ↓
7. Создаёт JWT-токен с user_id внутри
   ↓
8. Возвращает токен клиенту: {"access_token": "eyJhbG..."}
```

### При последующих запросах:

```
1. Клиент отправляет запрос с заголовком:
   Authorization: Bearer eyJhbGciOi...
   ↓
2. Система расшифровывает токен → получает user_id
   ↓
3. Проверяет, что токен не просрочен и не в чёрном списке
   ↓
4. Находит пользователя по user_id
   ↓
5. Проверяет, что is_active = true
   ↓
6. Пользователь определён → передаём дальше в обработчик
```

## 7. Как работает авторизация (проверка прав)

**Авторизация** = проверка «Тебе можно?»

### Шаг за шагом:

```
1. Пользователь уже аутентифицирован (мы знаем, кто он)
   ↓
2. У пользователя есть role_id (например, "role-user")
   ↓
3. Находим роль в roles.json → получаем permission_ids
   ↓
4. Для каждого permission_id находим разрешение в permissions.json
   ↓
5. Проверяем: есть ли среди разрешений то, что нужно?
   (resource = нужный ресурс И action = нужное действие)
   ↓
6. Если нашли → доступ разрешён, выполняем запрос
   ↓
7. Если не нашли → ошибка 403 "Доступ запрещён"
```

### Пример:

Пользователь Иван (роль "user") пытается удалить машину:

```
1. Роль "user" имеет разрешения: ["perm-cars-read"]
2. Разрешение "perm-cars-read" = resource: "cars", action: "read"
3. Иван хочет: resource: "cars", action: "delete"
4. "read" ≠ "delete" → разрешения НЕТ
5. → 403 Forbidden "Доступ запрещён: нет разрешения на delete для cars"
```

### Матрица доступов

| Ресурс | Действие | admin | user | moderator |
|--------|----------|-------|------|-----------|
| users | read | ✅ | ❌ | ✅ |
| users | write | ✅ | ❌ | ❌ |
| users | delete | ✅ | ❌ | ❌ |
| cars | read | ✅ | ✅ | ✅ |
| cars | write | ✅ | ❌ | ❌ |
| cars | delete | ✅ | ❌ | ✅ |
| roles | manage | ✅ | ❌ | ❌ |
| permissions | read | ✅ | ❌ | ❌ |

## 8. Как работает JWT-токен

**JWT** = JSON Web Token. Это строка из трёх частей, разделённых точками:

```
eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiJ1c2VyLTEiLCJpYXQiOjE3Nzk1MDkzMjN9.CNTLDgzkXfQtjH4a833wpfFy8I_Hl90oNvQkoY2Z3LY
\_________________/  \_____________________________________/  \______________________________________/
     HEADER                         PAYLOAD                                   SIGNATURE
```

### Header (заголовок)
Говорит, какой алгоритм использован для подписи:
```json
{"alg": "HS256", "typ": "JWT"}
```
Закодировано в Base64.

### Payload (данные)
Содержит информацию о пользователе:
```json
{
  "sub": "user-1",           // Subject — кто владелец токена (user_id)
  "iat": 1779509323,         // Issued At — когда токен создан (unix-время)
  "exp": 1779595723          // Expiration — когда токен истечёт (через 24 часа)
}
```
Закодировано в Base64. **Важно:** эти данные можно прочитать без ключа, поэтому мы НЕ кладём туда пароль или секреты!

### Signature (подпись)
Математическая подпись, которая гарантирует, что токен не подделан:
```
HMACSHA256(base64(header) + "." + base64(payload), SECRET_KEY)
```
Без секретного ключа нельзя создать правильную подпись. Поэтому подделать токен невозможно.

### Жизненный цикл токена:

```
1. Пользователь логинится → сервер создаёт JWT-токен
2. Клиент сохраняет токен и отправляет с каждым запросом
3. Сервер расшифровывает токен, проверяет подпись и срок
4. При logout → токен добавляется в чёрный список
5. Через 24 часа → токен автоматически перестаёт работать
```

## 9. Как хранятся пароли

### Почему нельзя хранить пароли в открытом виде?

Если кто-то получит доступ к базе данных, он увидит все пароли.
Это катастрофа — люди часто используют одинаковый пароль на разных сайтах.

### Что такое хеш?

Хеш — это результат математического преобразования.
Из пароля "qwerty123" получается строка вроде "a1b2c3d4e5f6...".
Обратное преобразование невозможно — из хеша нельзя получить пароль.

### Что такое соль (salt)?

Соль — случайная строка, которая добавляется к паролю перед хешированием.
Зачем? Если два человека используют пароль "qwerty123", без соли их хеши будут одинаковими.
С солью — каждый хеш уникален, даже если пароли одинаковые.

### Как это работает в нашем проекте:

```python
# ХРАНЕНИЕ ПАРОЛЯ (при регистрации):

1. Пользователь вводит пароль: "qwerty123"
2. Генерируем случайную соль: "a1b2c3d4e5f6a1b2"
3. Склеиваем соль + пароль: "a1b2c3d4e5f6a1b2qwerty123"
4. Хешируем SHA-256: "f7c3bc1d808e04732adf679965ccc34ca7ae3441"
5. Сохраняем: "a1b2c3d4e5f6a1b2:f7c3bc1d808e04732adf679965ccc34ca7ae3441"
              ^^^^^^^^^^^^^^^^ ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
              соль              хеш


# ПРОВЕРКА ПАРОЛЯ (при логине):

1. Пользователь вводит пароль: "qwerty123"
2. Из базы берём сохранённую строку: "соль:хеш"
3. Разделяем на соль и хеш
4. Склеиваем соль + введённый пароль: "a1b2c3d4e5f6a1b2qwerty123"
5. Хешируем SHA-256
6. Сравниваем с сохранённым хешем
7. Если совпадают → пароль правильный!
```

### Почему SHA-256, а не bcrypt?

- **bcrypt** — промышленный стандарт, специально созданный для паролей. Требует установку библиотеки `passlib[bcrypt]` и C-зависимостей.
- **SHA-256** — встроен в Python (модуль `hashlib`), не нужно ничего устанавливать. Для учебного проекта достаточно.
- В реальном продакшене нужно использовать bcrypt. Но для понимания принципов SHA-256 + соль — отличный выбор.

## 10. Что делает каждый файл — подробно

### app/main.py — Точка входа

Это «главный» файл. Когда мы запускаем `uvicorn app.main:app`, Python выполняет именно его.

**Что он делает:**
1. Создаёт приложение FastAPI
2. При старте — создаёт тестовых пользователей (если база пуста)
3. Подключает все роуты (users, admin, cars)
4. Добавляет корневой эндпоинт `GET /` для проверки

**Ключевые конструкции:**
```python
app = FastAPI(...)           # Создаём приложение
@app.on_event("startup")     # Функция запускается при старте
app.include_router(...)      # Подключаем роуты
@app.get("/")                # Обработчик GET-запроса на /
```

---

### app/database.py — Работа с JSON-файлами

Замена базе данных. Все операции — чтение и запись JSON-файлов.

**Функции:**
| Функция | Что делает |
|---|---|
| `read_data(filename)` | Читает JSON-файл, возвращает список словарей |
| `write_data(filename, data)` | Записывает список словарей в JSON-файл |
| `find_by_id(filename, item_id)` | Ищет элемент по полю `id` |
| `find_one(filename, **filters)` | Ищет первый элемент, где все фильтры совпадают |

**Пример:**
```python
# Найти пользователя с email "admin@test.ru"
user = find_one("users.json", email="admin@test.ru")
# Вернёт: {"id": "user-1", "email": "admin@test.ru", ...}
# Или None, если не найден
```

### app/models.py — Шаблоны данных (Pydantic-модели)

Pydantic-модели — это шаблоны, которые описывают, как должны выглядеть данные.
Они автоматически проверяют (валидируют) входящие данные.

**Зачем нужно?** Если клиент отправит email без собаки или забудет пароль — Pydantic сразу вернёт ошибку, до того как код попытается обработать некорректные данные.

**Основные модели:**

| Модель | Для чего |
|---|---|
| `UserRegister` | Входные данные при регистрации (ФИО, email, пароль, повтор пароля) |
| `UserLogin` | Входные данные при логине (email, пароль) |
| `UserUpdate` | Данные для обновления профиля (всё опционально) |
| `UserResponse` | Как пользователь выглядит в ответе API (БЕЗ пароля!) |
| `RoleCreate` | Данные для создания новой роли |
| `RoleUpdate` | Данные для обновления роли |
| `RoleResponse` | Как роль выглядит в ответе API |
| `PermissionResponse` | Как разрешение выглядит в ответе API |
| `TokenResponse` | Ответ при логине: `{"access_token": "...", "token_type": "bearer"}` |
| `MessageResponse` | Простой ответ с сообщением: `{"message": "Вы вышли из системы"}` |

**Ключевые конструкции:**
```python
class UserRegister(BaseModel):       # Наследуемся от BaseModel
    first_name: str                   # Обязательное строковое поле
    last_name: Optional[str] = None   # Необязательное поле (может быть None)
    email: str                        # Обязательное поле
    password: str                     # Обязательное поле
    password_confirm: str             # Обязательное поле
```

### app/security.py — Безопасность

Две главные задачи: **хеширование паролей** и **работа с JWT-токенами**.

**Функции для паролей:**

| Функция | Что делает |
|---|---|
| `hash_password(password)` | Хеширует пароль с солью, возвращает "соль:хеш" |
| `verify_password(password, hashed)` | Проверяет, совпадает ли пароль с хешем |

**Функции для JWT:**

| Функция | Что делает |
|---|---|
| `create_access_token(user_id)` | Создаёт JWT-токен для пользователя |
| `decode_access_token(token)` | Расшифровывает токен, возвращает payload или None |

**Ключевые конструкции:**
```python

import secrets                        # Встроенный модуль для генерации случайных строк
import jwt                            # PyJWT — единственная внешняя библиотека

secrets.token_hex(16)                 # Генерирует 32 случайных hex-символа
hashlib.sha256(...).hexdigest()       # SHA-256 хеш в виде hex-строки
jwt.encode(payload, SECRET_KEY, algorithm="HS256")  # Создание токена
jwt.decode(token, SECRET_KEY, algorithms=["HS256"]) # Расшифровка токена
```

### app/utils.py — Авторизация

Функция `check_permission()` — главная. Проверяет, есть ли у пользователя нужное разрешение.

**Что делает:**
1. Находит роль пользователя по `role_id`
2. Получает все разрешения этой роли
3. Ищет разрешение с нужным `resource` и `action`
4. Если не нашла → выбрасывает 403

**Ключевые конструкции:**
```python
def check_permission(user, resource, action):
    """Проверяет, есть ли у пользователя разрешение.
    Если нет — выбрасывает 403.
    Если да — ничего не делает (код продолжает работать)."""
    permissions = get_user_permissions(user)
    for perm in permissions:
        if perm["resource"] == resource and perm["action"] == action:
            return  # Нашли — всё ок!
    raise HTTPException(status_code=403, detail="Доступ запрещён")
```

## 14. Частые вопросы

### В: Почему JSON-файлы, а не PostgreSQL?

О: Для учебного проекта JSON проще — не нужно устанавливать и настраивать базу данных.
Принципы те же: читаем данные, ищем, фильтруем, записываем.
В реальном проекте нужно использовать PostgreSQL.

### В: Почему SHA-256, а не bcrypt?

О: SHA-256 встроен в Python (модуль `hashlib`), не нужно ничего устанавливать.
bcrypt требует C-библиотеки и установку через pip.
Для понимания принципов хеширования SHA-256 + соль достаточно.
В продакшене — используйте bcrypt.

### В: Что такое «мягкое удаление»?

О: Когда пользователь удаляет аккаунт, мы НЕ стираем его данные из базы.
Мы ставим `is_active = False`. После этого:
- Он не может залогиниться (проверка при логине)
- Его токен перестаёт работать (добавляется в чёрный список)
- Но данные остаются в базе (можно восстановить, можно анализировать)

### В: Чем аутентификация отличается от авторизации?

О: 
- **Аутентификация** = «Кто ты?» → проверяем email и пароль, выдаём токен
- **Авторизация** = «Тебе можно?» → проверяем разрешения у роли пользователя

Пример: у тебя есть пропуск в офис (аутентификация прошла),
но ты не можешь зайти в серверную (авторизация не прошла).

### В: Что будет, если токен украдут?

О: Кто-то сможет делать запросы от имени пользователя, пока токен не истечёт (24 часа) или пока пользователь не сделает logout (токен попадёт в чёрный список).
В реальных проектах: используют короткоживущие access-токены + refresh-токены, HTTPS, и другие меры.

### В: Зачем нужен чёрный список токенов?

О: JWT-токен — самодостаточный. Сервер не хранит информацию о том, кому выдал токен.
Если пользователь выходит из системы, нам нужно как-то запретить использование его токена.
Поэтому мы записываем токен в чёрный список и при каждой проверке смотрим — нет ли его там.

### В: Можно ли добавить новую роль?

О: Да, админ может создать роль через `POST /admin/roles`:
```bash
curl -X POST http://localhost:8000/admin/roles \
  -H "Authorization: Bearer <ТОКЕН_АДМИНА>" \
  -H "Content-Type: application/json" \
  -d '{"name": "viewer", "description": "Только просмотр", "permission_ids": ["perm-cars-read"]}'
```

### В: Что значит `--reload` при запуске uvicorn?

О: Сервер автоматически перезагружается при изменении кода.
Удобно при разработке — изменил файл, сохранил, сервер перезапустился.
В продакшене этот флаг НЕ используют.
